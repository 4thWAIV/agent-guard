## The standard (do not weaken)

Every OS/CLR primitive is reached only through its owned interface off the one `ISystemServices` container; a raw boundary call is a build error; green is reached by routing the call through the interface, NEVER by a suppression (`#pragma warning disable`, `[SuppressMessage]`, `NoWarn`, `severity = none`, or a dropped analyzer reference). The test projects are not exempt from the boundary rules. The one test way to build the container is `SystemServicesBuilder`.

#### `test-taxonomy-and-copy-on-write-simulator` (Tim ruled 2026-08-20 — resolves the IMPLEMENT wall)
The test system uses three test concepts:

#### `copy-on-write-simulator-design` (Tim ruled 2026-08-20 / 2026-08-21 — the simulator's exact shape)
Per filesystem call the resolution chain is three layers, in order: (1) any per-path `Handle` override the test set, then (2) the in-memory copy-on-write overlay holding this test's writes and created symlinks, then (3) the real read-only fixture folder underneath. Every write and every created symlink lands in the overlay, so the real fixture is never mutated — it can be built once and shared, and the simulator (unit) tests need no per-test cleanup or folder isolation. That isolation-and-cleanup requirement applies only to integration tests, which use `Real()` with no overlay and do write real disk.

**One shared overlay, one install call.** There is ONE internal `InMemoryFileSystemStore` — the copy-on-write overlay: a normalized-absolute-path→node map (file / directory / symlink / tombstone / inaccessible-flag) over an optional base, with the owned path comparer (default `StringComparer.Ordinal`, injectable) and the `CreateTempSubdirectory` uniqueness counter living ON the shared overlay. Both the filesystem fake and the platform fake take the SAME overlay by constructor; neither owns it. `SystemServicesBuilder.Real().SimulateFileSystem(...)` installs it — it does the underlying `Wrap`s across the four leaf interfaces and `IPlatformFileSystem` internally, all sharing the one overlay, each with the real interface injected as its base. That shared identity is the wall fix: a symlink created via `IPlatformFileSystem.MakeLinkTarget` lands in the overlay and resolves for `IFileReader.Exists`. The raw `Wrap<T>(Func<T,T>)` seam stays available for one-off single-interface fakes.

**Symlink resolution.** One routine both fakes call, walking the path segment by segment; when a resolved prefix is an overlay symlink it splices the target relative to the link's own parent directory and continues, with a bounded hop counter that throws `IOException` on overflow. Production's own layout is a two-hop chain (`bin/guard → ../current/guard`, and `current → versions/{v}`), so the resolver is multi-hop, not one-hop. It follows the final segment for the four leaf interfaces and does not for `IPlatformFileSystem`'s link ops (which target the link entry itself).

**Failure injection — `Handle`, first in the chain.** `OnFileSystem().Handle(path, (call, inner) => ...)` takes control of a specific path: for a matched path the lambda runs first and either throws any exception, returns an override, or delegates to `inner` to pass through. `MarkInaccessible(path)` is the kept convenience over it — one line that makes `EnumerateChildren(path)` throw `UnauthorizedAccessException` while `Exists(path)` still returns true — and this family of conveniences grows over time. This seam replaces the hand-rolled `ThrowingDirectoryEnumerator`, so no `.Tests` file hand-rolls a leaf implementer for a failure case (the prerequisite for `leaf-platform-single-implementer-rule`).

**Base supply — no `basedOn`.** The base is the real fixture, reached by `Wrap` over `Real()`; there is no in-memory `Fake(basedOn:)` container-over-container layering. It is dropped (YAGNI) until a real need appears.

**Builder-controlled simulator behaviors (Tim ruled 2026-08-21).** Two `IPlatformFileSystem` behaviors that the real disk otherwise decides are made builder-set options on the shared overlay, so a simulator (unit) test can exercise them instead of ceding them to the real-disk suite. (1) The executable bit: `NeedsExecutableFlag()` returns a builder-set value (default follows the real OS the test runs on; settable to simulate POSIX or Windows), and the overlay carries a per-node executable flag that `MakeExecutable`/`MakeNonExecutable` set and `IsExecutable` reads — all three throwing when the flag is unsupported, exactly as production does. So a test simulates POSIX, runs an install, and asserts the guard binary's exec bit through the simulator; this closes the fidelity gap where the fake previously hardcoded `NeedsExecutableFlag()=false` and never exercised the `chmod +x` path. The per-path set/get IS `MakeExecutable`/`MakeNonExecutable`/`IsExecutable`; the builder option is the `NeedsExecutableFlag` toggle. (2) Case-sensitivity: a builder option sets the shared store's case mode, which BOTH `IPlatformFileSystem.IsCaseSensitive` and the overlay's path comparer read (single owner — the comparer lives on the shared store); setting it to case-insensitive first scans the current store and throws if two existing paths collide under case-folding, because an insensitive filesystem cannot hold both.
