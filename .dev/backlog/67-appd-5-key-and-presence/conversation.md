# appd-5-key-and-presence — what Tim decided in conversation

This run covers GitHub issue #67 in full. The live issue is the authority; where it and this file disagree, the issue wins — except where a decision below explicitly replaces something the issue says, which is noted inline.

This decision was settled while working on issue #63 and is recorded here because it governs #67.

## Decisions

**appd does not ask for the user's presence when it starts. It asks the first time a client requests work.** This replaces the issue text, which currently reads "appd authenticates the user once at start" and "On all three platforms appd prompts once at start." Under this decision appd starts silently at login holding no unlocked key, and the presence check happens when a client actually asks for something that needs it. Tim's decision, in his words: "we only need the presence check once a client requests work done.  so lazy verify is better here as we have exposed nothing and it would be user jarring to be getting a check on login every time." The reasoning he gave is that nothing has been exposed until a client asks, and a prompt at every login is jarring for no gain. Issue #67's body still carries the older wording and should be brought into line before that work starts.

**appd loads the key on the first request that needs it, not at startup.** This travels with the presence decision above rather than being a separate choice: if reading the key requires a prompt, then loading it at startup is the startup prompt, and moving the presence check without moving the key load would leave the prompt exactly where it was. Once loaded the key stays in the process, which is the whole reason appd is long-running. What protects the key at rest — where it sits when appd is not running, and whether reading it requires the user — is not settled and is issue #67's to answer; this decision holds whichever way that goes, because if reading prompts then lazy loading is forced, and if it does not, lazy loading still keeps unlocked key material out of memory until something needs it.

**The key pair is minted by `agentguard install`, and the private key is protected by the guard itself rather than by an OS secure store.** Earlier work assumed an OS store had to hold it and kept concluding that no store lets a command-line tool authenticate once and then sign silently afterwards. Tim's answer walks around that: this product already protects directories from the AI, so the key sits behind the same mechanism everything else does. `install` is per-user — it places the binary under `~/.agentguard` — so the key belongs to the account rather than the machine, and a second account gets its own.

**Both key directories are hard-blocked from the AI, for reading and for writing.** The private key directory on the machine and the public key directory in the repository. Tim's words on why both matter: "IF the AI can write to the public key directory they can just mint their own key and check it in to the repo and then sign what they want (it looks the same to the system)." Blocking writes stops the AI minting its own identity and self-signing; blocking reads stops it taking the private key and signing outside appd, which would bypass the presence check the whole design exists to enforce. No bypass is currently foreseen for either, though one may be found later.

**appd holds the private key in memory and checks it has not changed.** Ordinary protected files are copied before an AI action and compared afterwards, because the user is free to change anything by hand and the guard must never fight the user. The key needs none of that. Tim's design: appd snapshots the private key once at start, loads it into memory, and before any action compares the on-disk hash against the one it holds. On a mismatch it raises the dashboard and works with the user to create a new key, restore the old one, or whatever puts them back in step. Because the working copy is in RAM, the key cannot be replaced underneath a running appd — a swap changes nothing about what gets signed, it only trips the alarm. The read block and this check do different jobs and both are needed: the block prevents theft, and the hash check detects tampering, which it cannot do for a read because reading leaves no trace.

**Every user working on a project mints their own key, and all the public keys are committed.** That is what lets anyone verify who signed which suppression, and it is why the folder is committed and why the AI cannot write to it. Tim's words: "Each user working on the project mints there own so that all other users can see who signed what suppresions (it also produces better evedence)." A consequence worth stating: because the folder is committed, adding a key to it is a pull request, so the act of granting somebody authority to sign is already a reviewed change with an author and a diff.

**There are two categories of signature, and they may eventually use different keys.** Some have to live in the repository and verify for anyone who clones it — signing a code suppression. Others live only inside one session — signing the decisions made during a run. Tim's words: "Technically they do not have to be the same key (but at first it is proabably cheaper to do it that way)." One key first. The reason to separate them later is not tidiness: a repository signature must verify years afterwards on a machine that has never met the signer, so that key wants longevity, while a session signature never leaves the machine and never verifies again, so that key could be generated per session and be worthless by morning.

**The signer is identified in the committed key record, and the identity is captured when the key is minted rather than looked up when it is verified.** At minimum the git username and email, gathered at project setup through the dashboard rather than read silently out of config. Tim also raised offering a GitHub login so a third party asserts the identity, which would open further capability for the large majority of users who have an account — that part is not yet decided. Whatever the source, the identity is written into the key record as a dated fact at minting time. Verification must never consult it live: a token expires, a hook has to answer offline and fast, and a signature has to verify years later on a machine that has never met the signer.

**A key is retired rather than removed, and retirement pins the signatures it stays good for.** Tim's decision, in his words: "we don't remove and revoke their key, we just update in a way where it can't be used for any new signtures but approved existing ones are still accepted." Retiring is a deliberate act: a command scans the repository for every live signature that key made, writes those identifiers into the key's own record, marks the key retired, and the result is committed. Verification then asks one of two questions — an active key's signatures are all good, and a retired key's are good only if the exact signature appears in its list. This deliberately does not use a timestamp on the signature, because the signing time is asserted by the signer's own clock and someone holding a retired key could set it back; and it needs no git history, which a hook cannot consult quickly or offline. It also handles editing correctly: changing a suppression a retired key signed changes the content, so the signature is no longer in the list and the change requires a current signer.
