## How a presence capability slots into the existing structure (grounded)
- `IPlatformServices` is the growth point (its own doc names "a biometric/keychain surface" as the intended addition). Presence = a NEW property on `IPlatformServices`, sibling to `FileSystem` (a distinct capability, not a filesystem op) — e.g. `IPresenceCheck Presence { get; }`.
- Governance analyzers AUTO-pick-up a new `IPlatformServices` property via `BoundaryServices.ResolveTree` (a reflective container-tree walk) — no rule-file edit needed: AG0010 (factory returns the container), AG0022 (one container implementer per compilation), AG0029 (Boundaries reaches per-OS only via `PlatformServices.Create()`), AG0019 (`SystemServicesBuilder.PlatformBuilder` must grow a matching `With`/`Wrap` or the build fails).
- The per-OS presence impl lives in the `CrossPlatform.MacOS/.Linux/.Windows` libraries (AG0008 confines P/Invoke to those four assemblies; the Tests project is NOT exempt). Pattern to mirror: `internal static partial class <Os>NativeMethods` with `[LibraryImport]`, `SetLastError=true` + `Marshal.GetLastPInvokeError`, `AllowUnsafeBlocks=true`.
- Testing: the one OS-agnostic spec project (`AgentGuard.CrossPlatform.Tests`) asserts the interface and RID-selects the impl; above-the-seam gating tests use the fake. Coverage: each per-OS assembly gated STANDALONE at a hard 75% (no override), aggregate on the Linux leg.

## Open decisions GROUND surfaced — resolve before the contract's Decisions lock
1. **THE WIRING MECHANISM (the crux).** `ApprovalGate.RequireApproval` is `internal static ApprovalDecision RequireApproval(string action)` — a bare STATIC taking only a string, no context/services, not injectable/substitutable. The seam comment and the PLAN both say the real check "drops in behind this call with NO change to the callers." But there is NO live mechanism for a per-OS presence service (on `IPlatformServices`) to reach `RequireApproval` without EITHER (a) changing its signature to take the context/service — which changes all three call sites (contradicting "no change to callers"), OR (b) `ApprovalGate` reaching a new static/global accessor (doesn't exist; cuts against the DI discipline). AND the plan requires it be fake-substitutable for above-the-seam testing, which a plain static class is not today. This is Tim's call.
2. **Presence is NOT POSIX-uniform.** The filesystem link-shares one Posix source across macOS+Linux; presence does not — macOS (`objc_msgSend`→LocalAuthentication), Linux (libpam+fprintd), Windows (WinRT/Win32→Hello) each need a SEPARATELY authored impl. Three distinct impl files, no shared body — confirm this is the intended shape.
3. **Coverage-exclusion — needed at all?** GROUND asks whether the untestable member even needs `[ExcludeFromCodeCoverage]`+AG0032-waiver, versus structuring the one truly-uncoverable line (the `evaluatePolicy` success path) to live where AG0032 already permits (an out-of-scope assembly) or as a one-per-OS owner (the AG0101 precedent shape). Decide: the interim waiver mechanism, or structure-to-avoid.
4. **ApprovalDecision shape.** Currently `(bool IsApproved, string Action, string Detail)` — free-text Detail, no machine-readable reason. Decide whether a denial needs a reason code (unavailable vs denied vs cancelled) for downstream handling, or the boolean + Detail suffices.
